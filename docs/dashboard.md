# Панель агента

[README](../README.md) · [Устройство сервиса](architecture.md) · [Эксплуатация](operations.md)

React-панель и API работают в том же Bun-процессе, что и агент. Отдельный
Node.js, dev-сервер или установка пакетов на компьютер не нужны. `docker compose
up --build` запускает панель на [localhost:3000](http://localhost:3000).
Авторизации самой панели пока нет; порт Compose привязан к `127.0.0.1`. HTTP-сервер принимает
только localhost-hostnames и запросы своего origin, ключи в браузер не передаются.

## Вход в аккаунт бота

В блоке «Аккаунт бота» есть вход через Twitch без ручного копирования токена.
Один раз [зарегистрируйте своё Twitch-приложение](https://dev.twitch.tv/console/apps)
типа **Public** и скопируйте его **Client ID** в форму панели. Если форма регистрации
требует Redirect URL, укажите `http://localhost:3000`; используемый Device Code Flow
не использует обратный редирект. Client Secret не требуется.

Нажмите «Войти ботом», затем «Открыть Twitch» и подтвердите права именно
аккаунтом бота. Панель дождётся подтверждения и покажет ник. Сам вход не запускает
комнаты и не отправляет сообщений. Код входа одноразовый и имеет ограниченный срок.
До подтверждения бот в новые комнаты не запускается.

Запрашиваемые права:

- `user:read:chat` — получать сообщения через EventSub.
- `user:write:chat` — отправлять сообщения.
- `moderator:read:chatters` — читать участников чата в каналах, где аккаунт бота
  является модератором или владельцем. Это не поимённый список зрителей видео.

Право на участников уже включено в авторизацию; загрузка и отображение этого
списка относятся к следующему этапу сцены.

Access token и refresh token остаются на сервере в `/data/twitch-auth.json`
с правами `0600` в томе `dashboard_data`. В браузер передаются только статус,
ник, права, Client ID и временный код входа. Хранилище — часть локальных данных,
его резервные копии содержат секреты. `config.json` сервис не изменяет.
Путь можно заменить `TWBIT_TWITCH_AUTH_FILE`, исходный публичный Client ID —
`TWBIT_TWITCH_CLIENT_ID`. Для обычного запуска эти переменные не нужны.

Сервис проверяет OAuth-сессию при запуске и раз в час. По истечении токена или
после HTTP 401 получает новую пару и сохраняет сменившийся refresh token.
Обновление общее для всех комнат, конкурентные отказы не расходуют одноразовый
refresh token повторно. Если вход отозван, комнаты останавливаются, нужен новый
вход. Сетевой таймаут отправки сообщения не вызывает повторную отправку.

Смена аккаунта и выход доступны после остановки комнат. «Выйти» удаляет локальную
сессию; полностью отозвать разрешение приложения можно в Connections на Twitch.
Если изначально заполнен `accessToken` конфига, старый режим продолжает работать
до перехода на OAuth. После выхода или отзыва OAuth скрытого возврата к старому
аккаунту нет. CLI без панели по-прежнему использует токен конфига.

Основание: [Device Code Flow](https://dev.twitch.tv/docs/authentication/getting-tokens-oauth/#device-code-grant-flow),
[проверка токенов](https://dev.twitch.tv/docs/authentication/validate-tokens/),
[обновление токенов](https://dev.twitch.tv/docs/authentication/refresh-tokens/),
[Get Chatters](https://dev.twitch.tv/docs/api/reference/#get-chatters).

## Комнаты

Первый запуск создаёт одну комнату из `channel`, `ai.delivery` и `speech.enabled`
в `config.json`. Далее список хранится отдельно: изменение канала в конфиге не
перезаписывает уже сохранённые комнаты. В интерфейсе можно добавить канал,
выбрать распознавание речи и режим ответов:

- **Сначала понаблюдать** — AI создаёт черновики, видимые в журнале и консоли.
  Отправка в Twitch и ежедневное приветствие отключены.
- **Общаться в чате** — после запуска доступны настоящие ответы и приветствие,
  если оно включено в конфиге и есть необходимые права Twitch.

Добавление комнаты не запускает её. Нажатие «Запустить агента» или «Запустить
в чат» создаёт отдельный сеанс `TwitchApplication`. Остановка дожидается
завершения запросов и записи очереди БД. Удалить можно только остановленную
комнату; её история и пользовательская память в PostgreSQL остаются.
Режим и звук выбираются при создании; чтобы изменить их в этой версии,
остановите комнату и добавьте её заново с нужными настройками.

### Ожидание эфира

Запущенная комната остаётся подключённой к чату и показывает «Ждёт эфир»,
пока Helix `Get Streams` не подтвердит трансляцию. Сообщения оффлайн-чата
видны в журнале, но не отправляются в AI и не становятся контекстом следующего
эфира. Бот не пишет, ASR worker и FFmpeg не запускаются. Это действует и для
комнат без звука, а также для прежнего CLI с чатом.

Проверка выполняется сразу после авторизации и затем раз в 15 секунд после
завершения предыдущей проверки. К задержке обнаружения добавляются время запроса
и обновление статуса в Twitch. Новых OAuth-прав не требуется:
[Get Streams](https://dev.twitch.tv/docs/api/reference/#get-streams) работает
с существующим пользовательским токеном.

При подтверждении эфира создаётся новый контекст AI, подключается звук, если
он включён для комнаты, и отправляется приветствие при готовом чате.
Прежние условия приветствия сохраняются: AI включён, режим отправки `chat`,
есть права записи и PostgreSQL, не более одной попытки в день на канал/аккаунт.
Переподключение звука и повторные проверки эфира не дублируют приветствие.

После обнаружения оффлайна текущие генерации отменяются, ASR и FFmpeg
останавливаются. Ответ из завершённого сеанса не переносится в новый эфир.
Если Twitch не может подтвердить статус, ответы и звук приостанавливаются до
успешной проверки; при восстановлении не нужно вручную запускать комнату снова.
Если запрос отправки уже был передан Twitch до обнаружения оффлайна, отозвать
его задним числом нельзя. Долговременные факты и аудит остаются в PostgreSQL.

Анонимный диагностический режим `--speech-only` сохраняет прежнее ожидание
публичного звука без токена и без чата.

Можно сохранить 24 комнаты и запустить до трёх одновременно. Все используют
один аккаунт Twitch, общую модель и настройки AI из конфига. У каждой комнаты
свои буфер разговора, расписание анализа, ASR worker и подключение к БД.
Память и история в общей БД разделены по каналу. Каждая дополнительная комната
со звуком увеличивает нагрузку на CPU и память; суммарные лимиты аккаунта Twitch
и провайдера AI остаются общими.

После перезапуска панель восстанавливает список, но оставляет все комнаты на
паузе. Настройки записываются атомарно в `/data/rooms.json` в томе
`dashboard_data`; путь можно заменить переменной `TWBIT_ROOMS_FILE`.
Этот файл содержит только канал, режим отправки, флаг звука и дату добавления.

## Сцена и журнал

Состояния «слушает», «думает», «проверяет ответ» приходят из реального цикла
`ReplyAssistant`, а после ответа на несколько секунд появляется его текст.
Облачко показывает этап работы, скрытое рассуждение модели не запрашивается.
«Настроение» — визуальное оформление текущего состояния, отдельного AI-запроса
для эмоций нет. Готовность чата и звука показана отдельно от соединения браузера
с панелью.

Журнал хранит последние 80 событий комнаты: сообщения чата, законченные ASR-фразы,
черновики, подтверждённые ответы, пропуски и ошибки. Тексты отображаются как текст
React без HTML. Метрики показывают только текущий сеанс комнаты; новый запуск
их сбрасывает. Токены включают генерацию и проверку; запросы без `usage`
отмечаются отдельно. Долговременный аудит и расход остаются в PostgreSQL.

Ошибки отправки содержат причину и код Twitch, например
`msg_followersonly_zero`: аккаунт бота должен отслеживать канал для участия
в чате. В истории решений эта же причина сохраняется в `outcome_reason`,
а код — в `error_code`. Отказ Twitch отличается от отсутствия подтверждения:
при таймауте неизвестно, доставлено ли сообщение. Автоматического повтора нет.
Неизвестные исключения остаются в серверном логе, их произвольный текст в панель
не передаётся.

Живой журнал и счётчики находятся в памяти процесса. Обновление страницы их не
сбрасывает, перезапуск комнаты или контейнера сбрасывает. Для долговременных
логов используйте [сохранение и backup](operations.md).

## Люди и отношения

На сцене показаны до шести активных авторов чата. Недавний подтверждённый ответ
подсвечивает связь агента с адресатом; черновик не считается реальным общением.
Активный — писал в последние пять минут при подключённом чате, это не список
зрителей видео. Учётная запись агента и основные сервисные боты исключены.

В блоке «Люди и отношения» есть поиск и фильтр активности. Нажатие на человека
открывает карточку: сообщения текущей сессии, до 12 сохранённых фактов и моментов,
до 20 решений с ответами из PostgreSQL и выбранный стиль общения. Отправленные,
отклонённые ответы, ошибки и черновики подписаны отдельно. Промпты, API-запросы и
скрытые рассуждения в карточку не попадают. При недоступной БД доступен стиль и
сессионные сообщения. История привязана к Twitch user ID, а не отображаемому имени.

Стиль задаётся вручную: «Как со всеми», «Свой человек», «Подкалывать», «Помягче»,
«Не трогать». Заметка до 240 символов описывает общение, не становится фактом в
памяти. Стиль применяется к следующим анализам запущенного агента без перезапуска;
«Не трогать» дополнительно проверяется кодом перед доставкой и после review.
Настройки не отменяют запрет слов и проверки фактов. Конфиг `ai.banter` даёт
начальный стиль «Подкалывать»; ручной выбор имеет приоритет.

Отношения сохраняются атомарно в `/data/people.json` в том же Docker volume, до
500 настроек по всем каналам. Пути можно задать `TWBIT_PEOPLE_FILE`. В снимке комнаты
не более 100 человек и 20 последних сообщений каждого. Сессионная активность
сбрасывается при новом запуске комнаты; настроенные люди остаются в списке.
Эмоциональные оценки или проценты симпатии не выдумываются. Стиль действует в
режиме панели; отдельный CLI без неё не читает её настройки отношений.

## Локальный API

| Запрос | Действие |
|---|---|
| `GET /api/state` | Снимок всех комнат без конфига и ключей |
| `GET /api/events` | SSE-события `state` со снимками и heartbeat каждые 15 секунд |
| `POST /api/rooms` | Добавить `{channel, delivery, speech}` |
| `POST /api/rooms/:channel/start` | Запустить комнату |
| `POST /api/rooms/:channel/stop` | Остановить комнату |
| `DELETE /api/rooms/:channel` | Удалить остановленную комнату |
| `GET /api/rooms/:channel/people/:login` | Карточка зрителя с памятью и историей |
| `PATCH /api/rooms/:channel/people/:login` | Сохранить `{style, note}` и применить к следующим ответам |
| `POST /api/auth/device` | Начать вход: `{clientId}` |
| `POST /api/auth/cancel` | Отменить ожидающий вход |
| `POST /api/auth/check` | Повторно проверить сохранённый вход |
| `POST /api/auth/logout` | Удалить локальную сессию, все комнаты должны быть остановлены |

Изменяющие запросы требуют JSON и `Content-Type: application/json`; для команд
без параметров передайте `{}`. Ответы не кешируются. Обновления SSE объединяются
на 150 мс, число клиентов ограничено 16; отставший браузер переподключается.

## Разработка и проверка

`web/` содержит React и CSS, `src/dashboard/` — API и управление комнатами,
`src/auth/` — OAuth и хранилище токенов,
`src/stream/` — проверка статуса и управление сеансом эфира,
`src/runtime/events.ts` — типизированные события. Наблюдатель изолирован от
основного агента: ошибка отображения не прерывает чат или анализ.
`bun run build:web` внутри Docker собирает статические файлы в `dist/` встроенным
сборщиком Bun. Они обслуживаются тем же HTTP-сервером.

Docker-сборка выполняет typecheck, тесты с подменёнными AI/Twitch-клиентами и
сборку React без сети. Тесты проверяют изоляцию комнат, конкурентные команды,
сохранение, перезапуск, SSE, ограничения HTTP и отсутствие ключей в снимках.
Рабочий конфиг и секреты в тестовый образ не копируются.

Для прежнего одиночного режима без панели можно заменить команду Compose
`["--dashboard"]` на `[]` или передать аргументы через `docker compose run --rm
twbit --chat-only`. Параллельный запуск в тот же канал может привести к повторным
ответам, поэтому сначала остановите его в панели.
